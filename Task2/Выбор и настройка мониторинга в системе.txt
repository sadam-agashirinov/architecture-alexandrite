*Мотивация.
	Добавление мониторинга в систему поможет определить 
	1. слабые места в системе
		например, один инстанс БД который работает на чтение и на запись
		или CRM API который может не справлятся с нагрузкой из-за большой очереди заказов, 
		которые MES система поместила в очередь. так же возможно сама очередь сообщений не справляется 
		с той нагрузкой которая на нее идет от MES API.
		
	2. пиковые нагрузки как на систему в целом, так и на отдельные ее компоненты.
		например, понять при каких пиковых значениях нагрузки проседает скорость расчета изделия у MES API.
		
	3. ценные бизнес-инсайты
		возможно некоторые функции системы клиенты используют не по назначению 
		или иначе чем задумывалось бизнесом.
		
	4. степень безопасности системы.
		определить в какой степени безопасности находятся данные клиентов, 3D-модели изделий.
		Возможно клиенты загружают уникальные и авторские модели изделий, нужно предотвращать их кражу 
		как со стороны несанкцианированного доступа клиентов так и персонала компании.
	
Все это дает картину происходящего с системой под разными углами, что поможет правильно усилить, улучщить,
доработать и подготовить систему под возврастающие нагрузки.

*Выбор подхода к мониторингу

1. Для всех API в системе стоит использовать подход "Четыре золотых сигнала".
2. Для фронтенда CRM стоит использовать RED.
3. Для Shop DB, MES DB и RabbitMQ стоит использовать RED.
4. Для хранилища 3D-моделей стоит использовать USE.


*Метрики для отслеживания.
1. RabbitMQ
	Number of dead-letter-exchange letters -  поможет понять кол-во не доставленных сообщений до адресата.
	Number of message in flight - поможет понять загруженность очереди.
	
	Эти две метрики помогут понять на сколько сильно загружена очередь сообщений и CRM API получающий данные от MES API.
	
2. Shop API, CRM API, MES API

	Number of requests (RPS) - отображает общий трафика проходящего через API.
		Поможет отслеживать сколько запросов обрабатывает API в единицу времени, спрогнозировать нагрузку на систему 
		в определенное время что позволит лучше планировать масштабирование. 
		Резкие скачки RPS могут свидетельствовать о ненормальной активности, 
		например, о DDoS-атаке или проблемах с клиентами (например, бесконечные циклы запросов).
	Number of requests (RPS) per user - среднее кол-во запросов в секунду от одного пользователя.
		Позволит выявить пользователей с подозрительной активностью, что позволит ограничить или 
		оптимизировать использование ресурсов, а так же применить меры защиты от злоупотреблений.
	
	
	CPU % - процент использования процессора сервером, на которм работает API.
		Высокое назрузка может означать недостаточную мощность системы для обработки запросов.
		Если процент использования CPU постоянно высокий возможно стоит увеличить вычичлителные
		мощности за счет улучшения текущего сервера или добавления новых серверов.
		Мониторинг загруженности CPU поможет предотвратить сбои и задержки в работе API.
	Memory Utilisation - процент использования оперативной памяти сервером.
		Высокий процент использования может сигнализировать о большом потреблении памяти, чем ожидалось.
		Если процент использования памяти постоянно растет это может стать признаком утечки памяти.
		Мониторинг загруженности оперативной памяти поможет предотвратить сбои и задержки в работе API.

	
	Response time (latency) - время, которое требуется API для обработки запрос и отправки ответа.
		Высокий показатель метрики может плохо сказаться на пользоватьском опыте,
		может сигнализировать о проблемах на сервере, с сетью или кодом API
		(например, был использован медленный алгоритм обработки данных или стоит добавить кеширование).
	Number of simultanious sessions - Количество одновременных сессий, активных на сервере в момент времени.
		Большое значение данного показателя может означать высокий уровень использования API,
		это важно для понимания пиковых нагрузок и масштабируемости.
	
	Kb tranferred (received) - количество данных полученных API от клиента.
		Поможет в оценке трафика, пропускной способности сети.
		Большой объем трафика может свидетельствовать о проблемах или необычных активностях (боты, атака).
		
	Kb provided (sent) - количество данных отправленных API клиентам.
		Если объем передаваемых данных велик, это может указывать на необходимость оптимизации передачи 
		(например, сжать ответы или использовать более эффективные форматы данных).
	
3. Shop DB, MES DB

	Memory Utilisation for db instance - процент использования RAM на сервере БД.
		Если использование памяти достигает 100%, это может привести к сбоям в работе базы данных, 
		особенно если система начинает использовать диск как виртуальную память (что значительно медленнее).
		Мониторинг памяти позволяет понять, насколько эффективно используется кэш и индексы базы данных. 
		Недостаток памяти может привести к снижению производительности запросов, 
		особенно при работе с большими объемами данных.
		
	Number of connections for db instance - количество активных соединений в БД.
		Позволяет понять загруженность БД. Если максимальный лимит соединений достигнут - это может 
		привести к отказам в обслуживании новых запросов.
		Так же позволяет анализировать активность пользователей и приложений.
		
	Size of db instance - размер БД.
		Поможет понять когда БД достигнет предела своих ресурсов, что позволит во время увеличить объем хранилища.
		Чем больше размер базы данных, тем больше ресурсов требуется для выполнения запросов (например, сканирование больших таблиц). 
		Понимание размера базы данных позволяет предпринять шаги по оптимизации запросов, индексов или использования сжатия данных.
		В облачных решениях размер базы данных напрямую влияет на стоимость хранения данных. 
		Мониторинг помогает контролировать расходы на хранилище и предотвращать излишние затраты.
	
4. S3 Storage
	Size of S3 storage - размер  хранилища S3.
		Можно настроить уведомления на основе метрики размера хранилища для предотвращения неожиданного увеличения затрат 
		или управления хранением данных в критических ситуациях.
		
*План действий

	1.Как показывает С4 диаграмма заказы хранятся в двух разных БД: ShopDb и MES db.
		Понятно что в ShopDb хранятся заказы сделанные через приложение, а в MES db - заказы из API.
		Но в этом и проблема, что нет центрального хранилища инфы о заказе 
		и сервиса отвечающего за бизнес-логику заказа.
		Думается мне что лучше создать МС отвечающий за заказы со своей БД.
	2.Долгая загрузка первой страницы MES.
		Тут думаю хорошо бы добавить кэширование.
	3.Ручное тестирование.
		Возможно какие-то сценарии тестирования можно автоматизировать и 
		запускать при деплое MR в dev-окружение, при создании релизной ветки или перед деплоем в прод.
	4.Базы данных имеют один инстанс, который работает на запись и на чтение.
		Это проблема т.к. идет нагрузка на БД.
		Можно применить паттерн CQRS для решения этой проблемы.
	5.Ручной деплой в release и production окружения.
		Автоматизировать деплой в эти среды.
