* Существующие и потенциальные проблемы:
	1. Линейное увеличение нагрузки на систему.
	2. Пробелемы с долгим выполнением заказов, хотя производственных мощностей хватает.
		Скорее всего тут проблема со сменой статуса заказов из-за чего заказ не попадает на производство.
		Так же стоит внедрить решение из п.10.
	3. Долгая загрузка первой страницы MES.
		Тут думаю хорошо бы добавить кэширование.
	4. Увеличение времени расчета стоимости изделия в MES при большом кол-ве полигонов.
	5. После открытия API добавились жалобы со стороны пользователей API.
		Заказ в этом случае создается в CRM через получение сообщение из очереди от MES.
		Возможно очередь перегружена и не успевает за нагрузкой, 
		а так же возможно что CRM не успевает обрабатывать большое кол-во заказов из MES.
	6. Так же есть проблема во взаимодействии API интернет магазина и хранилища 3D-моделей изделий.
		Думается мне что стоит сделать их взаимодействие асинхронным через очередь сообщений.
	7. Ручное тестирование.
		Возможно какие-то сценарии тестирования можно автоматизировать и 
		запускать при деплое MR в dev-окружение
	8. Базы данных имеют один инстанс, который работает на запись и на чтение.
		Это проблема т.к. идет нагрузка на БД.
		Можно применить паттерн CQRS для решения этой проблемы.
	9. Ручной деплой в release и production окружения.
	10.Как показывает С4 диаграмма заказы хранятся в двух разных БД: ShopDb и MES db.
		Понятно что в ShopDb хранятся заказы сделанные через приложение, а в MES db - заказы из API.
		Но в этом и проблема, что нет центрального хранилища инфы о заказе 
		и сервиса отвечающего за бизнес-логику заказа.
		Думается мне что лучше создать МС отвечающий за заказы со своей БД.
	11. Так же одной из патенциальных проблем может стать S3 хранилище 3D-моделей изделий.
		Место в хранилище может закончится.
		Как вариант можно задать некоторый срок хранения моделей после которого их можно удалить.

*Пути решения:
	1. Создать МС отвечающий за заказы со своей БД.
	2. Применить паттерн CQRS в работе МС отвечающего заказы при взаимодействии с БД.
	3. Для решения из п4 возможно стоит ограничить максимальное кол-во для изделия, 
		а так сделать взаимодействие с MES API асинхронным, задачи для расчета стоимости изделия можно ставить 
		в очередь. Плюс к этому можно увеличить кол-во инстансов API или 
		выделить логику по расчету стоимости в отдельный сервис, с которым будем взаимодействовать асинхронно.
		Будем ставить задачи по расчету стоимости изделия в очередь.
	4. Автоматизировать часть сценариев тестирования и запускать при деплое MR в dev-окружение.
	5. Автоматизировать деплой в release и production окружения.

*Какой я вижу архитектура приложения в будущем?
	1. В системе появится МС отвечающий за работу с Заказами со своей БД.
		Это будет способствовать централизации работы  с заказами и ее статусами.
		Так же применить паттерн CQRS при работе с БД.
	2. Отделить от MES логику отвечающую за расчет стоимости изделени. 
		Выделить ее в отдельный МС и сделать работу с ней асинхронной.
		То есть МС будет получать задания по расчету стоимости изделия из очереди сообщений.

В случае увеличения нагрузки можно увеличить кол-во инстансов МС.
